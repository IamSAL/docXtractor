⏺ ---
  Three Approaches

  ---
  A. Thin HTTP wrapper (plain fetch/axios)

  Rename OllamaService → LlmService, replace the ollama npm package with raw
  fetch or Axios calls to FreeLLM's /v1/chat/completions. Remove the node pool,
  health check interval, and model-pull logic entirely — FreeLLM absorbs all of
  that.

  Trade-offs: Minimal deps, full control. But you write the OpenAI response
  deserialization by hand, no TS types for the API shape.

  ---
  B. openai npm package pointing at FreeLLM ⭐ recommended

  Install openai npm package, set baseURL: http://freellm:3000/v1 and apiKey: 
  "freellm" (FreeLLM doesn't require a real key for internal use). The SDK
  handles request/response types, retries, and streaming. LlmService becomes a
  thin NestJS wrapper around openai.chat.completions.create(...).

  Trade-offs: One extra dep (openai), but you get full TS types, streaming
  support for free, and it's the de-facto standard for OpenAI-compatible
  clients. Zero friction if you ever add another OpenAI-compatible gateway
  later.

  ---
  C. Provider abstraction layer

  Define an ILlmProvider interface with complete(messages, opts) method.
  FreeLlmProvider implements it. Module resolves the concrete provider from
  config.

  Trade-offs: More files, more indirection. Useful if you plan to support
  multiple simultaneous backends — but FreeLLM already IS the multi-provider
  abstraction. This would be abstraction on top of abstraction. Overkill here.

  ---
  Recommendation: B. The openai package is the standard OpenAI-compatible
  client, gives you free TS types, and reduces boilerplate vs raw fetch. FreeLLM
   is designed to be drop-in compatible with it. No over-engineering.

  Which approach do you want to go with?
